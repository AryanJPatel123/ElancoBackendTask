# Tick Sightings Backend: Elanco Placement Task

**Author:** Aryan J Patel

This is the backend for the tick sightings tracker. It downloads raw sighting data from the
Elanco API, cleans it, removes duplicates and stores it. Then provides an API to search
the sightings and to report on them, plus a small web page for trying the API in a browser.

| Brief requirement | File code is in |
|---|---|
| Data handling (large datasets, duplicates, incomplete data) | [`Ingest.py`](Ingest.py) |
| Search and filtering by time range and location | [`search_filters_endpoint.py`](search_filters_endpoint.py) (`GET /sightings`) |
| Sightings per region | [`search_filters_endpoint.py`](search_filters_endpoint.py) (`GET /reports/by-region`) |
| Trends over time (weekly / monthly) | [`search_filters_endpoint.py`](search_filters_endpoint.py) (`GET /reports/trends`) |
| Error handling (API failures, data inconsistencies) | [`Ingest.py`](Ingest.py) (retries, quarantine table, sync log) and [`search_filters_endpoint.py`](search_filters_endpoint.py) (input validation, `/sync/status`, `/health`) |
| AI/ML insights (extension) | Not done; see [What I would do with more time](#what-i-would-do-with-more-time) |

## How to run it

**Requirements:** Developed on Python 3.13.x

```bash
#Make sure to cd into the project folder first
# 1. Create and activate a virtual environment
python -m venv .venv
.venv\Scripts\activate          # Windows
# source .venv/bin/activate     # macOS / Linux

# 2. Install the dependencies
pip install requests pydantic fastapi uvicorn

# 3. Download the data from the Elanco API into ticks.db
python Ingest.py

# 4. Start the API
uvicorn search_filters_endpoint:app --reload
#If uvicorn is still not recognised, add uvicorn to your PATH, or run python -m uvicorn search_filters_endpoint:app --reload
```

Then open:

- **http://127.0.0.1:8000/**: the search page (filters, results table, per-region and trend charts)
- **http://127.0.0.1:8000/docs**: interactive API documentation, where every endpoint can be tried
- **http://127.0.0.1:8000/redoc**: Additional documentation about the API \
/docs and /redoc are autogenerated endpoints by FastAPI, contents are inferred from the defined endpoints within the code

Other commands:

```bash
python Ingest.py --self-test          # run the built-in tests
python Ingest.py --benchmark 200000   # time a load of 200,000 generated records
```

`python Ingest.py` can be run again at any time to refresh the data. Records it has already
stored are skipped, so running it repeatedly is safe and uses minimal resources. The API reads from `ticks.db` by
default; set the `TICKS_DB` environment variable to point it at a different database if wanted.

## Architecture

```
  Elanco API                       Ingest.py                              ticks.db (SQLite)
  /data/tick-sightings  ──GET──▶  fetch data
                                    │
                                    ▼
                                  hash each payload ──── seen before? ──▶ skip
                                    │ new
                                    ▼
                                  store raw payload ───────────────────▶ raw_sightings
                                    │
                                    ▼
                                  validate + clean ──── unusable ──────▶ quarantine
                                    │ ok
                                    ▼
                                  merge with existing row ── conflict ─▶ quarantine
                                    │
                                    ▼
                                  update and insert ──────────────────────────────▶ sightings
                                  record run stats ────────────────────▶ sync_runs

  Browser / client ──HTTP──▶ search_filters_endpoint.py (FastAPI) ──read-only──▶ ticks.db
```

The system has two separate parts that share one database:

1. **Ingestion (`Ingest.py`)** is the part that writes data to the database. It
   pulls everything from the API, and brings the database up to date (and adds a log of when the last database update was).
2. **The API (`search_filters_endpoint.py`)** opens the database in read-only mode and answers
   queries. Because the two endpoints (Elanco and the locally defined endpoint here) are separate, a slow or failing sync never takes the API down: the
   API keeps serving the last good data.

### Database tables

| Table | Contents                                                                                                                      | Why it exists                                                                                                              |
|---|-------------------------------------------------------------------------------------------------------------------------------|----------------------------------------------------------------------------------------------------------------------------|
| `raw_sightings` | Every distinct payload exactly as received, with a SHA-256 hash and fetch time                                                | Lets the data be reprocessed if cleaning rules change, without calling the API again; makes repeat syncs easy/cheap to run |
| `sightings` | Cleaned data, exactly one row per sighting `id`                                                                               | Table the API queries to display data at the endpoint                                                                      |
| `quarantine` | Records that could not be used, or that conflicted with stored data                                                           | Unuseable/bad data is visible and can be fixed instead of being dropped silently                                           |
| `sync_runs` | One entry per sync: start/finish time, status, fetch stats (number of record fetched, inserted, merged etc), errors (if one occurred) | Monitoring; shown by using `/sync/status`                                                                                  |

## API reference table

| Endpoint | Description                                                     |
|---|-----------------------------------------------------------------|
| `GET /sightings` | Search sightings with filters, sorting and pagination           |
| `GET /sightings/{id}` | A single sighting (returns 404 if not found)                    |
| `GET /locations` | Cities in the data, with sighting counts                        |
| `GET /species` | Species in the data, with latin name and sighting counts                       |
| `GET /reports/by-region` | Number of sightings per region (city), with percentages         |
| `GET /reports/by-species` | Number of sightings per species, with percentages               |
| `GET /reports/trends` | Sightings per week or per month                                 |
| `GET /sync/status` | When the data was last refreshed, and whether it was successful |
| `GET /health` | Whether the database is readable                                |

### Filters

`/sightings` and all `/reports/*` endpoints will accept the same filters:

| Parameter | Example | Notes                                                           |
|---|---|-----------------------------------------------------------------|
| `start` | `2023-01-01` or `2023-01-01T09:00:00` | Inclusive. Time zone offsets are accepted and converted to UTC. |
| `end` | `2023-03-31` | A date on its own is inclusive of the whole day.                |
| `city` | `city=London&city=Leeds` | Repeat to select several cities. Not case-sensitive.            |
| `species` | `species=Marsh tick` | Repeat to select several species. Not case-sensitive.           |
| `include_incomplete` | `false` | Hides sightings that have any missing field. Default `true`.    |

Additional parameters:

- `/sightings`: `sort=date_desc|date_asc`, `limit` (default 50), `offset`
- `/reports/trends`: `interval=weekly|monthly` (default monthly), `fill_gaps=true|false` (default true).
  Weekly periods are labelled with the date of the Monday that starts the week.

### Examples

```
GET /sightings?start=2023-01-01&end=2023-03-31&city=london&limit=10
GET /reports/by-region?start=2024-01-01
GET /reports/trends?interval=weekly&start=2023-01-01&end=2023-02-01
```

### Errors

| Status | When                                                                                                                                 |
|---|--------------------------------------------------------------------------------------------------------------------------------------|
| `422` | Invalid input, e.g. `start=yesterday`, `start` after `end`, `limit=10000`, or a date range too large to fill with empty time periods |
| `404` | Unknown sighting id                                                                                                                  |
| `503` | Database missing (run `python Ingest.py`) or unreadable                                                                              |

Errors raised by this code are of the form `{"detail": "<message>"}`. Errors from
FastAPI's own parameter validation (e.g. `limit=10000`) use FastAPI's standard format, where `detail`
is a list naming each invalid parameter.

## Design decisions

### Technology choices

- **Python.** Strong libraries for both HTTP and data validation, and quick to build an MVP in.
- **FastAPI** for the API. Validates query parameters from Python type hints, generates the interactive `/docs` page for free, and is built on
  pydantic, which the ingestion code already uses.
- **pydantic** for validating records. It parses the many ISO-8601 date formats, errors
  say exactly which field failed and why. Those messages go into the quarantine table.
- **requests + urllib3 `Retry`** for calling the API. Retries with backoff are configured rather
  than hand-written.
- **SQLite** for storage. No server to install, database is one file, and easily
  fast enough for this data (see [Performance](#performance)).
- **No front-end framework.** `index.html` is plain HTML/CSS/JavaScript. The task is backend-focused,
  so the page only needs to show the API working, and it has no build step or dependencies.

### Data handling

**Large datasets**
- Records are processed in chunks of 500. Memory use stays flat however large the response,
  and the batched `IN (?, ?, …)` lookups stay under SQLite's 999-parameter limit which was enforced on older versions.
- Each chunk needs two batched lookups
  instead of one query per record, and writes use `executemany`.
- **One transaction per chunk.** Committing every record would take a very long time, one huge transaction
  would hold the write lock for the whole load. If a load fails part-way, only the current chunk is
  rolled back, and re-running will continue where it was stopped.
- **Content hashing.** Every payload is hashed (SHA-256 with keys sorted, so key order
  doesn't matter). Payloads already stored are skipped, so a repeat sync of unchanged data does
  almost no work (Claude's tests determined that it took 1.8 s for a repeated 200,000 records, versus 45.7 s for the first run-through).
- **Indexes match the queries:** date, city + date, species + date, and an expression index (result of a calculation on a column) on
  `strftime('%Y-%m', observed_at)` for the monthly trend report.
- **WAL mode** lets the API keep reading while a sync is writing.

**Duplicates**
- Exact duplicates (identical payloads) are detected by hash and skipped.
- Same `id`, different content is merged field by field. Copies of a record often have
  different blank fields, so blanks are filled from whichever copy has a value, giving a more
  complete entry than both individual copies.
- If two copies have different values for any field, there is no way to determine which is
  correct. The first-seen value is kept and the disagreement is
  written to the `quarantine` table for a person to review, rather than guessed at by the program.
- `id` is the primary key of `sightings`, so a duplicate can never become two rows.

**Incomplete data**
- Only **`id` and `date` fields are required**. Without an id duplicate records can't be detected, without a
  date it can't be placed on a timeline. Records missing either field are quarantined with the given reason.
- Missing `location`, `species` or `latinName` (API sends `""` or whitespace) are stored as
  `"Incomplete"` rather than dropping the record or storing NULL. A partial sighting is still a
  real sighting and still counts towards trends, and reports show an explicit "Incomplete" group
  instead of losing rows.
- Each row stores a **completeness score** (0–3, the number of those three optional fields filled in), so
  the API can hide incomplete rows with `include_incomplete=false` without checking three columns.

**Cleaning**
- Dates are converted to UTC with no timezone attached and stored as ISO-8601 text. SQLite has
  no date type, and ISO strings naturally sort in time order, so range filters are just simple comparisons.
- Dates in the future are rejected.
- City names are not case-sensitive so "london", "LONDON" and "London" count as one region.

### Search and filtering

- **One shared `Filters` class** (injected with FastAPI's `Depends`) builds the SQL `WHERE` command
  for `/sightings` and every report. All of them will accept the same filters, so reports and searches with the same parameters always cover the same rows.
- **No SQL injection.** `WHERE` clauses are built only from fixed text fragments; every value is
  passed as a bound parameter. The sort direction comes from a `Literal` type, so only the two
  allowed values ever reach the SQL.
- Dates are parsed by hand rather than with FastAPI's `datetime` type. The error message can then
  name the field and give an example, and the code knows whether a time was given, so
  `end=2023-03-31` includes the whole of 31 March instead of stopping at midnight the night before.
- Pagination uses `limit`/`offset` with a separate total count, so a client can show "page 3 of
  20". Results are ordered by date then `id`, so rows with the same timestamp can't repeat or be
  skipped between pages. `limit` is capped at 500.
- Multiple cities or species can be selected at once (`IN (...)`).

### Reporting

- **Aggregation happens in SQL** (`GROUP BY` + `COUNT`), so only one small row per region or period
  comes back to Python, however many sightings there are.
- Reports include percentages and a total, sorted most-first.
- **Region = city.** The data only contains city names, so each city is treated as a region. Mapping
  cities to wider areas (e.g. "North West England") would require extra referencing data.
- Weeks start on Monday and are labelled with that date (e.g. `2023-01-02`). I avoided SQLite's
  `%W` week number because it behaves oddly around the new year (can sometimes misnumber weeks, unsure why).
- **Gap filling.** `GROUP BY` only returns periods that have sightings, so a quiet month would just
  be missing and a line chart would draw straight across it. Trends fill missing periods with zero
  across the requested date range. This is capped at 5,000 periods so a request like
  `start=0001-01-01&interval=weekly` can't exhaust memory.

### Error handling

**API failures (during ingestion)**
- **Automatic retries** on 429 (rate limited) and 500/502/503/504 (server errors), up to 5 times with
  exponential backoff (0 s, 2 s, 4 s…), respecting `Retry-After` if requested by the server. Other 4xx errors are not
  retried, since repeating a bad request won't fix it.
- **Timeouts** (5 s to connect, 30 s to read), so a hung server (one that doesn't,
  or may as well not respond) can't freeze the sync.
- **The response shape is checked**: anything that isn't a JSON list fails with an error.
- **Existing data is never damaged by a failed fetch.** The whole download finishes before anything
  is written. The failure is recorded in `sync_runs` and the script exits with code 1, so a
  scheduler can detect it.

**Data inconsistencies**
- Unusable/conflicting records go to `quarantine` with the reason
  (e.g. `invalid: date: Input should be a valid datetime or date, invalid character in year`, or
  `conflict: city: kept 'London', ignored 'Leeds'`).

**In the API**
- Invalid input gives a 422 with a message that says what to fix.
- A missing database gives a 503 telling you to run `Ingest.py`, rather than SQLite quietly
  creating an empty file and having every query failing with "no such table".
- Any other database error becomes a JSON 503 rather than a 500 crash page.
- The API opens the database as read-only, so it can never change the data.
- `/sync/status` shows both the last run and the last successful run. After a failure you can
  see that the refresh failed and how old the data being served is.
- `/health` runs a real query, so "healthy" means the database can actually be read.

## Performance

Results of `python Ingest.py --benchmark 200000` (generated data: 200,000 sightings
plus about 2% duplicates with a missing field and 5% records with no species):

| Operation | Result                                                  |
|---|---------------------------------------------------------|
| Initial load of 203,959 records | 45.7 s (about 4,500 records/s)                          |
| Repeat sync, nothing changed | 1.8 s                                                   |
| Date-range query (one year, 12,486 rows) | 65 ms; query plan confirms, it uses `ix_sightings_date` |
| City + date query | 9 ms                                                    |
| Sightings per city | 16 ms                                                   |
| Monthly trend | 13 ms                                                   |

## Testing

`python Ingest.py --self-test` runs against an in-memory database and checks:

- duplicate copies with different blank fields are merged into one complete row;
- a conflicting copy is quarantined and the original value kept;
- an unparseable date, a future date and a missing id are each quarantined;
- a second identical sync changes nothing;
- a simulated network outage is recorded as `failed` and leaves the stored data intact.

The self-test and benchmark code (the end of `Ingest.py`) was written with the help of Claude (an AI
assistant), as noted in the source.

## What I would do with more time

- **AI/ML insights (extension task):** e.g. forecast next month's sightings per city with a simple
  seasonal model, flag unusual spikes as possible outbreaks, or cluster cities with similar
  seasonal patterns.
- **Real regions:** map cities to UK regions or postcodes and add coordinates so sightings can be
  shown on a map.
- **Scheduled syncs:** run ingestion automatically (cron or a background task) instead of by hand.
- **A proper test suite:** move the self-test into pytest and add API tests using FastAPI's `TestClient`.
- **Pinned dependencies:** add a `requirements.txt` with exact versions.
- **Incremental fetching:** if the API supported paging or a "changed since" filter, fetch only new
  records instead of downloading everything each time.
- **Production readiness:** PostgreSQL, Docker, authentication and rate limiting, CORS settings for a
  separately hosted front end, and keyset pagination for very deep result pages.
- **A quarantine review endpoint**, so conflicts can be inspected and resolved through the API.
